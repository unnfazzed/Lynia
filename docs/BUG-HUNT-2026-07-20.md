## Sibling-sweep

**BH-23** — pattern signature: a `SecureStore`-backed key exported from a `logic/*` module that must be
wiped on sign-out per the S1 shared-device invariant, but isn't yet in `clearDeviceState()`'s delete list.

```
grep -rn "RIDER_BID_DRAFT_KEY\|RIDER_SENT_OFFERS_KEY\|PICKUP_CHECKLIST_DRAFT_KEY\|deleteItemAsync" apps/mobile/src/auth/session.ts
grep -rn "^export const [A-Z_]*KEY" apps/mobile/src --include=*.ts | grep -v __tests__
```

Enumerated every exported `*_KEY` constant across `apps/mobile/src/logic/`, `src/auth/`, `src/net/`
against the ~26-key delete list in `clearDeviceState()` (`session.ts:528-580`). `RIDER_SENT_OFFERS_KEY`
was the sole gap — every other per-user/per-session key (order draft, KYC draft, saved places/recipients,
pending-rating/topup/confirm-items markers, rider identity, rider job snapshot, pickup-checklist draft,
delivery codes + their index) is already present in the list. Fixed above, no sibling left unaddressed.

**BH-24** — pattern signature: a client-side type declaring a field `string` while the API sends it as a
raw JSON number (or vice versa), specifically where a `typeof`-gated restore guard would silently discard
a legitimately-shaped-but-differently-typed persisted value.

```
grep -rn "ratingAvg" --include=*.ts --include=*.tsx .
grep -n "Float\|Decimal" apps/api/prisma/schema.prisma
grep -rn "typeof parsed\." apps/mobile --include=*.ts --include=*.tsx
```

`ratingAvg` appears in 6 other mobile call sites beyond the fixed one:
`order-offers.ts:24,34` (`Number(o.rider.ratingAvg)` — tolerant of either wire shape, not a sibling),
`order/[id].tsx:780` and `CounterOfferCard.tsx:64` (pass-through props into `RiderMini`, which itself does
`Number(ratingAvg).toFixed(1)` — tolerant, and neither site persists the value, so no corruption risk),
`LiveTrackingCard.tsx:113` (reads the already-fixed `riderIdentity.ratingAvg`, not the raw offer). The
`typeof parsed.*` sweep found exactly one other hit outside `rider-identity.ts`
(`apps/mobile/src/api/client.ts:275`, gating on an HTTP error body's `message` field — a field the app's
own error-mapping code constructs as a literal string, not sourced from a Prisma numeric column, so
genuinely not a sibling). `ratingAvg` was the sole field in the codebase with this specific
declared-string/actual-number mismatch feeding a strict-`typeof` restore guard — fixed above.
