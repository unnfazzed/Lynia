## Findings

Four new findings, all LOW–MEDIUM, all fixed in this PR with regression tests. Full detail (file:line,
root cause, fix) is in `docs/KNOWN_BUGS.md` under "Bug hunt 2026-07-14 night"; summarized here:

### BH-03 — `KYC_MODE=manual` was invisible to the mobile client (MEDIUM)

`KYC_MODE=manual` is a documented production fallback (`env.ts`: "…or manual review (`KYC_MODE=
manual`)") — no vendor session, an ops reviewer resolves it instead. The server already modeled this
correctly (`becomeRider` returns `mode`, `retryKyc` in manual mode is an intentional pending no-op), but
the mobile client never read `mode` anywhere:

- `become.tsx` always showed *"Verification started. Finish it in the browser, then come back and go
  online"* after a manual-mode submit — describing a browser step that never opens.
- The rider-home pending screen always showed *"Continue verification"* wired to `retryKyc`, whose
  manual-mode response has no `verificationUrl`. `resolveKycRetryFeedback` treated any missing URL as a
  hard failure, so every tap produced a false *"Couldn't start verification — try again in a moment."*
  error — a genuinely successful (200) request masquerading as a broken one, on a loop with no way to
  silence it.

**Fix.** `retryKyc` now returns `mode` on *both* branches (previously only the vendor-submit path did).
`getProfile` surfaces the deploy-wide `KYC_MODE` as `rider.kycMode` — a global config value, not a
per-rider column, but the cheapest way to make it visible to the static pending screen without forcing a
mutation round-trip. `resolveKycRetryFeedback` takes `mode` and returns a calm `info` line instead of
`error` when a missing URL is the *expected* shape of a manual-mode success. `become.tsx` and the rider
pending `EmptyState` both branch on mode with honest copy and drop the dead "Continue verification"
button in manual mode.

### BH-04 — lost-response retry on rider signup hit a dead-end 409 (LOW-MEDIUM)

`becomeRider` succeeding server-side with the HTTP response dropped/timed-out (a real client-timeout
scenario per `client.ts`'s 15s cap) left the rider on the submit form; retapping Submit hit the server's
existing "Already registered as a rider" 409, surfaced as a plain unrecoverable error with no way off the
form — even though the rider's account was actually fully set up.

**Fix.** The 409 now carries a structured `reason: "already_rider"` (matching the existing
`{reason, message}` convention already used for online-gate refusals elsewhere in this codebase, instead
of a bare message string the client would have to regex-match). `become.tsx` special-cases that reason to
clear the stale KYC draft and navigate to `/rider`, landing the rider on their real, already-registered
status screen.

### BH-05 — rider's own "offer sent" card could show the wrong price after an edited retry (LOW-MEDIUM)

Repro: rider sends fare=$10 → response lost to a network blip → the error state re-enables the compose
form → rider edits the fare to $12, unaware the $10 already landed → retaps Send → hits the server's
"already responded" 409 → the client's own lost-response recovery path (added specifically to handle
"did it actually go through?") re-read the CURRENT `fare`/`etaNum` component state to build the "your
offer is in" card — showing the just-edited $12 as the rider's bid, while the server and the customer
both have $10 on record. Not a financial-integrity bug (the server is authoritative and the customer
never sees the wrong number) but a genuine self-trust bug in the rider's own UI.

**Fix.** `offerM`'s mutation now carries `{fare, fareNum, etaNum}` as explicit variables — react-query
hands the same variables object to both `onSuccess` and `onError`, so the recovery path always has the
values that were actually sent, not whatever the form shows later. The card-construction logic moved
into a new pure `buildSentOfferEntry(order, sentFare, sentEtaNum)` so the invariant is unit-testable
without mounting the screen.

### BH-06 — a rating armed just before an app kill was silently dropped (LOW-MEDIUM)

`RatingCard`'s rating-on-tap arms a 4s undo window and correctly flushes an armed rating on React
**unmount** (navigating away mid-window) — that path is tested and works. It does *not* handle an
OS-level app kill in the same window: a bare `setTimeout` + `useRef` closure is destroyed outright, with
no unmount effect to run. A customer who taps a star, sees "Submitting N★…", and swipe-kills the app
(a routine "I'm done" gesture) loses the rating — self-healing only if they happen to reopen that
specific order again. This stood out against the codebase's own established pattern of durably
persisting every other completion-journey in-flight action (delivery-code rotation, confirmItems,
push-token registration) against exactly this failure mode.

**Fix.** `RatingCard` gains `onArm`/`onUndo` callbacks, fired synchronously and independently of the
undo timer. `order/[id].tsx` persists a durable `pendingRating` marker (new `session.ts` functions,
mirroring the existing `confirmItemsPending` marker) the instant a star is armed, clearing it on Undo or
confirmed success. A new pure `reconcilePendingRating` (mirroring `reconcileConfirmItemsPending`)
re-sends a still-pending rating against the live order snapshot on every refresh (cold start, warm
foreground) while the order is still `delivered` (ratable) with no rating recorded yet — the order's own
transition to `status: "completed"` on a successful `rateOrder` IS the "already rated" signal, since the
live tracking snapshot carries no separate rating field. Wired into `clearDeviceState` so the marker
never survives a shared-device sign-out.
