## AMBIGUOUS — flagged for a human

1. **`docs/IR-RUNBOOK.md:49`** — "Abusive authenticated user → ban via the admin console
   (suspend/ban), which revokes their access." In code, `admin-riders.service.ts` `banRider`/
   `suspendRider` set `accountStatus` and stop future privileged actions, but never touch
   `Session.revokedAt` — a banned rider's existing access/refresh tokens keep authenticating until
   they expire naturally. This is a real behavioral gap in an incident-response runbook (the kind
   of claim you don't want to discover is wrong during an actual incident). Two ways to close it:
   reword the runbook to be precise ("blocks future actions; pair with an explicit session revoke
   for urgent cases"), or have ban/ban-adjacent actions also revoke active sessions. Left to a
   human because it's a product/security tradeoff, not a doc typo.

2. **`docs/DATA-RETENTION.md:28`** — "Device tokens: deleted on sign-out (already)." The backend
   only deletes a token when the mobile client explicitly calls
   `DELETE /notifications/device-token`; `POST /auth/logout` itself never touches `device_tokens`.
   Whether the mobile sign-out flow actually calls the unregister endpoint is outside
   `apps/api/src` — needs a mobile-side check to confirm or correct.
