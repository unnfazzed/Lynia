## Phase 2 — what changed

### RF-10 — `apps/mobile/src/auth/session.ts` (PR #375)

`session.ts` mixed the real auth `Session` (load/save/clear/deviceId) with ~10 unrelated
per-order/per-flow SecureStore groups. Added 3 characterization tests **first** (the existing
`session.test.ts` had only 4 cases) pinning `clearDeviceState()`'s exact wiped-key set —
including the oddities: the device id, onboarding-seen, and permissions-primed flags are
install-level and deliberately survive sign-out; the session token is cleared separately by
`clearSession()`. Then moved every non-auth group **verbatim** into a new `device-state.ts`;
`session.ts` re-exports them via `export * from "./device-state"` so none of its 17 existing
importers (verified by grep — all named imports) needed to change.

**Unplanned fix found during verification:** CI's `depcruise` step failed — the split routes 3
*pre-existing* circular-import cycles (`client.ts`↔`session.ts`, `session.ts`↔`history-store.ts`,
`session.ts`↔`last-active-store.ts`, all already in `.dependency-cruiser-known-violations.json`)
through the new `device-state.ts` file via the `export *` hop, which the allowlist didn't
recognize by name. Confirmed via a clean main-vs-branch baseline diff (regenerated in the same
fully-installed workspace, branch-switched rather than compared across worktrees with partial
`node_modules` linking, which had produced spurious results on a first attempt) that the only
change was the expected extra hop — regenerated the baseline via `pnpm run depcruise:baseline`
and committed it as a follow-up commit on the same PR.

**Evidence:** `pnpm typecheck && pnpm build && pnpm test` green pre+post (1169 api + 520 mobile
tests, +3 net new — nothing removed/weakened). `pnpm lint` 0 new warnings. `pnpm run depcruise`
0 new violations after the baseline regeneration. 1126 raw changed lines across 2 commits (over
the ~400-line guideline) — same "byte-identical single-concern move" exception the ledger
already granted RF-02/RF-06: nothing was rewritten, only relocated.

### RF-11 — `apps/api/src/privacy/privacy.service.ts` (PR #376)

`eraseAccount` was a single ~300-line method (preflight standing gate → in-tx CAS anonymise →
rider/PII scrub → post-commit GCS purge). Split into four named private helpers — `preflight()`,
`anonymiseProfileTx(tx, …)`, `scrubPiiTx(tx, …)`, `postCommitPurge(…)` — each carrying its
original comments verbatim (every CAS/TOCTOU justification preserved word-for-word), the tx
client threaded explicitly, and no reordering of any operation inside the transaction.

Renamed the ledger's placeholder `scrubRiderTx` → `scrubPiiTx`: that block also scrubs
non-rider-specific free text (rating comments, issue descriptions, report notes, order
`cancelReason`) and the standalone PII stores/GPS trails, not just rider fields.

No characterization tests were needed — the existing 494-line `privacy.service.spec.ts` (31
cases) already pins `eraseAccount`'s full behavior end-to-end, per the ledger's sensitive-adjacent
disposition for this file (mechanical extraction only).

**Evidence:** `pnpm typecheck && pnpm build && pnpm test` green pre+post (1169 api tests
unchanged — same count, extraction only). `pnpm lint` 0 new warnings. `pnpm run depcruise` 0 new
violations (this file has no dependency-graph changes). No public surface touched:
`eraseAccount`/`purgeExpiredData` signatures, the `DELETE /auth/me` route, and `packages/shared`
are all untouched — only new `private` methods added. 488 raw changed lines (over the ~400-line
guideline) — same exception as above.
