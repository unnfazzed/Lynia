| BH-25a | **Customer never learns a stale rider recovered — `presence:recovered` role:"rider" is never emitted, and even if it were, the customer's socket hook had no listener for it.** The C5 presence-escalation mechanism is asymmetric: the customer→rider direction (BH-08) emits `presence:recovered` role:"customer" from `markCustomerPresent` whenever a previously-escalated customer's socket (re)subscribes, and the rider's socket hook (`use-rider-job-socket.ts`) listens for it. The mirror direction was never built — `scanPresence()`'s stale-rider recovery loop (`tracking.gateway.ts`, formerly lines 634-639) dropped the order from `staleNotified` and released the cluster-wide escalation claim, but never called `emitPresenceRecovered(id, "rider")`; and the customer's own socket hook (`use-order-socket.ts`) had no `presence:recovered` listener at all. The failure mode isn't hypothetical: `scanPresence`'s own `riderLiveInRoom` self-heal path (a heartbeat-write-lag false positive, not a real GPS gap) touches the DB heartbeat with **no accompanying `position` WS push** — so once escalated, the customer's "rider may be offline — call your rider" card had no server signal to clear until the ride's next status transition. | `apps/api/src/tracking/tracking.gateway.ts`, `apps/mobile/src/realtime/use-order-socket.ts` | MEDIUM | **FIXED** — the recovery loop now calls `this.emitPresenceRecovered(id, "rider")` when an order drops out of `staleNotified` (mirroring `markCustomerPresent`'s existing call for the reverse direction); `use-order-socket.ts` gained a `presence:recovered` role:"rider" listener that calls `refetchOrder()` — the same REST self-heal `connect`/`connect_error` already use — so a self-heal with no fresh GPS tick still picks up the freshly-touched `rider.updatedAt` and clears the stale card. |
| BH-25b | **`boardSubscribe`'s room re-scope is not atomic — two overlapping calls on the same socket can leave a rider joined to both a stale board room and the fresh one, defeating geo-scoping.** `TrackingGateway.boardSubscribe` re-scopes a rider's board rooms with `await isBoardEligible(...)` then a `for (const room of client.rooms) { ... await client.leave(room) }` loop then a join loop — none of it guarded by any per-socket lock, and Socket.IO/NestJS does not serialize concurrent event invocations for the same client. The mobile client legitimately fires two `board:subscribe` emits close together on the same socket (`use-rider-board.ts`'s `connect` handler and its separate loc-change effect — the exact profile of a rider app resuming from background), so a second call's leave/join loop can interleave against the first's still-in-flight mutation of the shared, mutable `client.rooms` Set. ## Sibling-sweep

**BH-25a** — pattern signature: an `emitPresenceRecovered(orderId, role)` call site, or a mobile socket
hook subscribing to `WS_EVENTS.presenceRecovered`.

```
grep -rn "emitPresenceRecovered" --include="*.ts" apps packages
grep -rn "presenceRecovered" --include="*.ts*" apps/mobile/src
```

2 hits before the fix: the sole existing call site (`markCustomerPresent`, customer→rider direction,
already correct) and the sole existing listener (`use-rider-job-socket.ts`, the rider's hook, already
correct). The rider→customer direction was the only gap on both the emit side and the listener side —
both closed above. Re-ran both greps after the fix: `emitPresenceRecovered` now has 2 call sites
(customer direction unchanged + the new rider direction) and `presenceRecovered` has 2 listeners
(`use-rider-job-socket.ts` unchanged + the new `use-order-socket.ts` listener) — symmetric, no gap left.

**BH-25b** — pattern signature: `for (const room of client.rooms) { ... await client.leave(room) }` (or
the RemoteSocket twin `for (const room of s.rooms)`) with no per-socket serialization.

```
grep -rn "for (const room of client.rooms)\|for (const room of s.rooms)" --include="*.ts" apps
```

3 hits, all in `tracking.gateway.ts`:
- `boardSubscribe` (the confirmed bug) — **fixed** via `runBoardOpSerialized`.
- `boardLeave` — **fixed** (confirmed vulnerable sibling: same live-`client.rooms`-Set shape, racing
  against `boardSubscribe` from the same two mobile call sites) — wrapped in the same serialization.
- `kickRiderFromBoard` (KB-BOARD-REVOKE) — iterates a **snapshot** `RemoteSocket.rooms` from
  `server.fetchSockets()`, a different object from the live `client.rooms` Set `boardSubscribe`/
  `boardLeave` mutate, so it is **not** vulnerable to the exact mutate-while-iterating interleave that
  causes stale-room accumulation. It has a related but distinct TOCTOU instead (a concurrent
  `boardSubscribe` joining a fresh geo room AFTER the kick's snapshot was taken survives the kick) —
  **left OPEN, not fixed**, logged below with reasoning: the method's own docstring already documents it
  as best-effort/non-security ("a missed kick just means a few stale board cards until the next
  reconnect, never a bypass" — every real bid path re-gates standing independently), and closing it
  would need a cluster-wide lock across `fetchSockets()`'s remote-socket boundary, disproportionate to a
  cosmetic, self-healing-on-reconnect gap.
