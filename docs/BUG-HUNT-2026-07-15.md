## Findings

### BH-07 — rider's "rate the sender" star tap had zero durability across an app kill (MEDIUM)

BH-06 (customer rating) and UX15-01 (rider delivered/undelivered terminal) both established durable
markers for exactly this failure class — an in-memory-only action on the frozen post-delivery terminal
silently lost to a process death before its response lands. The rider's own optional "rate the sender"
star tap (`rider/job.tsx`) never got the same treatment: a tap fires `senderRateM.mutate(n)` with no
persisted marker anywhere, so an app kill before the POST resolves drops the rating outright. Worse, a
*lost response* (not a lost request) surfaced as a scary, unrecoverable-looking error on retry: `rateSender`
correctly rejects a repeat with a 409 "Order already rated", but the mutation's `onError` treated every
error identically — rolling back the star and showing a generic failure — instead of recognizing that,
for a one-per-rider rating, that specific 409 IS confirmation the earlier attempt landed.

**Fix.** A durable `pendingSenderRating` marker (`session.ts`, mirroring `pendingRating`/
`RiderJobTerminal`) is persisted the instant a star is tapped, before the POST resolves; a new pure
`reconcilePendingSenderRating` (`rider-job.ts`) decides whether to retry it, gated on matching the
terminal currently on screen so a resolved retry never writes its confirmation onto a different,
not-yet-rated job. Both the live mutation and the retry now treat a 409 as confirmation (thank-you state),
not failure. 5 new cases in `rider-job.test.ts`.

### BH-08 — rider's "customer may be offline" warning never self-cleared mid-delivery (LOW-MEDIUM)

`customerStale` (rider/job.tsx) is a one-way sticky flag set on `presence:stale` role:"customer" and
cleared only on the order's next status change — "the flow progressing implies things are moving again"
per its own comment. For a delivery leg that sits at one status for a while (e.g. a long `en_route_dropoff`),
a customer whose app blipped offline and reconnected left the rider staring at a stale, now-inaccurate
warning for the rest of that leg with no way for it to self-correct. (The customer-side equivalent,
`isRiderTrackingStale`, doesn't have this bug — it's recomputed from a live GPS timestamp every render,
so it self-heals the moment ticks resume; only the rider-side customer-presence flag lacked an
equivalent recovery signal.)

**Fix.** New `presence:recovered` WS event (`packages/shared/src/contracts.ts`), emitted from
`TrackingGateway.markCustomerPresent` the moment a customer who HAD been escalated re-subscribes (only
when there was a genuine prior escalation to cancel — an ordinary subscribe stays a no-op). The rider's
`useRiderJobSocket` gains an `onCustomerRecovered` callback wired to clear `customerStale` immediately.
No schema migration; additive wire event. Tests: `tracking.gateway.spec.ts` (updated the existing
re-subscribe test to assert the new emit + a new no-escalation-no-emit case) and
`use-rider-job-socket.test.tsx` (3 new cases).

### BH-09 — wallet top-up had no idempotency key, unlike every other money-moving path (MEDIUM, LOW today)

`POST /wallet/topups` (`WalletService.createTopup`) took no dedup key, unlike `CreateOrderRequest`
(customer order-create) and every admin wallet mutation (`creditManual`'s `idemKey`), both of which
exist specifically because a client-side timeout+retry is a real, documented scenario in this codebase.
A rider whose top-up request succeeded server-side but whose response was lost to the 15s client timeout,
then retapped "Send request", created a second, distinct `pending` `TopUp` row for the same attempt — no
live rail-confirmation poller exists yet to double-credit today, but it's a real gap by the codebase's
own established pattern and becomes an actual duplicate-charge vector the moment that follow-on ships;
in the meantime it already orphans a stray pending intent with no user-visible explanation.

**Fix.** `CreateTopupRequest` gains an optional `idempotencyKey` (mirroring `CreateOrderRequest`);
`TopUp` gains a nullable `idempotencyKey` column + a partial unique index on `(rider_id,
idempotency_key)` built CONCURRENTLY (migrations `0028_topup_idempotency_column` /
`0029_topup_idempotency_index`, mirroring the order-create idempotency migrations 0020/0021).
`WalletService.createTopup` dedupes on it (pre-check + P2002 fallback for a concurrent race), same
shape as `OrdersService.create`. The mobile top-up screen generates one key per top-up *attempt*
(rotated only in `reset()`, which is the one path that starts a genuinely new attempt — a same-attempt
retry after an error, still on the amount step, reuses it). 3 new cases in `wallet.service.spec.ts`.

### BH-10 — "raise price & send again" mid-auction created a duplicate live order (MEDIUM-HIGH)

During the last 20s of a still-open auction (the `urgent` flag) or the "no riders online" empty state,
`order/[id].tsx` offers a "Raise price & send again" button that carries the order's route/price into
the compose flow — but only ever navigated, never cancelled the original. Submitting the prefilled form
created a brand-new order while the ORIGINAL stayed fully open for offers, biddable, and selectable —
risking two riders dispatched for one physical parcel, or the customer negotiating/paying attention on
two fronts at once. Every OTHER call site of the same `rebroadcast()` function (expired/cancelled/
undelivered terminals) is already terminal and has nothing to cancel — this was the one path that fires
on a still-live order.

**Fix.** New pure `shouldCancelBeforeRebroadcast(orderStatus)` (`order-tracking.ts`) — true only for
`open_for_offers`. `rebroadcast()` now cancels the current order first (best-effort: a 409 or network
failure still lets the customer proceed to compose, rather than stranding them) before navigating, gated
on this helper so the five already-terminal call sites are unaffected. A `rebroadcasting` loading state
guards the two live-state buttons against a double-tap. 2 new cases in `order-tracking.test.ts`.

### BH-11 — KYC photo permission denial had no recovery path (MEDIUM)

`become.tsx`'s `pickFrom` (camera/gallery capture for the mandatory KYC photo) showed a plain error
string on a denied permission and nothing else. Once the OS stops re-prompting (`canAskAgain: false`
after a "Don't Allow"), that error is the end of the road — unlike the location-permission gate
elsewhere in the app (`rider/index.tsx`), which offers "Open location settings". A rider who denies both
camera and gallery permission is permanently blocked from onboarding, since `photoKey` (required for
submission) can never be set.

**Fix.** New pure `shouldOfferPermissionSettings(perm)` (`gates.ts`). `pickFrom` checks it on a denial
and, when true, an "Open settings" button (`Linking.openSettings()`) appears alongside the existing
camera/gallery buttons — mirroring the location gate's pattern. 3 new cases in `gates.test.tsx`.

### BH-12 — rider bidding compose card's "Cancel" button wasn't disabled while the offer send was in flight (LOW-MEDIUM)

`rider/index.tsx`'s bid compose card offers "Accept"/"Send my price" (which can take several seconds —
the UI itself shows "Still sending — hang on" after 4.5s) alongside a "Cancel" button with no pending
guard, unlike its sibling dismiss controls (`BailSheet`, `UndeliveredSheet`), which both correctly
`disabled={pending}`. Tapping Cancel while a send was in flight dismissed the card immediately without
aborting the request: on success the offer still landed and later reappeared unannounced as a "Your
offers" card for a bid the rider believed they'd cancelled; on failure the resulting error rendered on an
already-dismissed screen with no visible context.

**Fix.** `disabled={offerM.isPending}` on the Cancel button, matching the sibling sheets. Trivial prop
wiring with no natural pure-function extraction and no existing render-test harness for this screen — not
independently unit tested, consistent with precedent for similarly-shaped fixes in past sweeps
(UX15-08's `cancelM.onError` refresh, UX15-11's `refetchInterval` gating).

### Not independently fixed — a design observation, not a new defect

While investigating BH-10, the customer-journey research pass also noted that `OrdersService
.activeForCustomer` (the query behind the home screen's "delivery in progress" recovery banner) returns
only the single most-recently-updated live order via `findFirst`, with a code comment explicitly
acknowledging "(rarely) more than one is live". With BH-10 fixed, the one code path that could silently
create a second live order without the customer intending it is closed; the residual case (a customer
deliberately sending two separate parcels back-to-back) is intentional multi-order use, not a bug, and
the older order remains reachable via Trip History (no status filter) even though it drops off the one
proactive recovery banner. Left as a documented limitation rather than a fix — surfacing multiple live
orders on the home banner is a UI scope change beyond a bug-hunt-sized diff, not a one-line correction.
