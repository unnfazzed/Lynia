same PR since they share one root cause (an unstamped audience signal).

**BH-19** — pattern signature: a durable retry marker's reconcile function that clears on an
orderId mismatch instead of leaving the marker in place for a generic (non-single-active-order) route.

```
grep -rn "!== pending\.orderId\|!== pendingOrderId\|pending\.orderId\|pendingOrderId" apps/mobile/src apps/mobile/app --include=*.ts --include=*.tsx | grep -v __tests__
grep -rln "reconcilePendingRating\|reconcilePendingSenderRating\|reconcileConfirmItemsPending\|reconcilePendingTopup" apps/mobile
grep -rn "!== pending\|!== .*\.orderId\|pending\.orderId\|pendingOrderId\|order\.id !==" apps/admin apps/api packages --include=*.ts --include=*.tsx | grep -v __tests__
```

4 hits across the 4 reconcile-style functions in the codebase. `reconcileConfirmItemsPending`
(`rider-job.ts:87-98`) clears on mismatch too, but confirmed a NON-sibling: it's consumed only by
`rider/job.tsx`, which is exclusively mounted for the rider's single current active job
(`getActiveOrder()`) — "a different order is active" genuinely means the old one is gone there, unlike
the generic `/order/:id` route. `reconcilePendingSenderRating` and `reconcileRiderJobTerminal` already
had the correct wait/leave-in-place pattern. Only `reconcilePendingRating` needed the fix — no server-side
(`apps/api`) or admin-side (`apps/admin`) siblings exist for this client-only durable-marker pattern.

**BH-20** — pattern signature: a client-side sticky flag driven solely by a live room-broadcast WS event
with no reconciliation against ground truth on (re)subscribe/reconnect.

```
grep -rn "presence:stale\|presence:recovered\|presenceStale\|presenceRecovered" apps packages
grep -rn "customerStale\|riderStale\|customerPresence\|riderPresence" apps
```

2 hits. `customerStale` in `rider/job.tsx` is the only client-side presence-sticky flag anywhere in the
app; there is no rider-presence-shown-to-customer sibling (the customer's own tracker doesn't render a
"rider may be offline" banner at all — position staleness there is driven by a separately-computed
timestamp comparison, not a sticky WS-set flag, so it's structurally immune to this class). One call site
to fix, on the server side where the reconciling sync now lives.
