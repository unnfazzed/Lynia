## Phase 1 — target selection

Churn recompute (45-day window): highest-churn files are config/manifest churn
(`apps/mobile/package.json`, `app.config.ts`, `CHANGELOG.md`, `apps/api/src/config/env.ts`) — not
refactor targets. The ranking is otherwise stable versus the 2026-07-21 hotspot map. Per the
routine's priority order — (a) resume an in-flight migration first — the top pick was **RF-05**
(`apps/api/src/tracking/tracking.gateway.ts`), already scoped in `docs/RF-05-WS-GATEWAY-STATE.md`
with step 1 described as "move the five structures + their helpers into a `tracking-presence.ts`
module ... gateway calls unchanged."

**Finding on inspection:** the design doc's step 1 undersold the entanglement. Of the five
in-memory structures, only `positionEmit` (the position-coalescing subsystem: `coalescePositionEmit`
/ `flushPositionEmit` / `prunePositionRooms`) is genuinely isolated — no shared state with the other
four, no cross-calls into the gateway's presence/emit methods beyond the one `flush` callback. The
other four (`staleNotified`, `customerStaleNotified`, `customerPresence`, `customerSocketOrders`)
are woven through `handleDisconnect`, `subscribeOrder`, `scanPresence`, `scanCustomerPresence`,
`customerLiveInRoom`/`riderLiveInRoom`, and cross-call the gateway's own `emitPresence*` methods and
`server.fetchSockets` — moving all five in one PR as the design doc suggested would have been a
much larger, riskier diff than "move a map + helpers," on the single riskiest file in the codebase
(most BH-/DS- entries in `KNOWN_BUGS.md` trace back to this gateway).

**Decision:** split RF-05 step 1 into RF-05a (position-coalescing — done this run) and RF-05b (the
remaining four structures — re-scoped as its own design question, left OPEN). This keeps the PR
small, single-concern, and safe, at the cost of not finishing RF-05 step 1 in one run — consistent
with the routine's "small, single-concern, atomic PRs" rule over the design doc's original (looser)
estimate.

No other target was picked up this run. The two other OPEN, not-yet-scoped hotspots
(`apps/mobile/app/rider/index.tsx` — bid-adjacent, `apps/admin/app/lib/adminTypes.ts` — a
public-surface/contract design question) both remain explicitly flagged in the ledger as needing a
design pass before they're mechanical-refactor-safe, not a change from prior runs' assessment.

## Phase 2 — refactor (RF-05a)

**What changed:** extracted the position-emit coalescing subsystem out of `TrackingGateway` into a
new `PositionCoalescer` class (`apps/api/src/tracking/position-coalescer.ts`):
- Moved: `positionEmit` map (renamed `rooms` inside the new class), `CoalesceState`,
  `PositionPayload`, `POSITION_COALESCE_MS`, `POSITION_ROOM_TTL_MS`, and the buffering/timer logic
  from `coalescePositionEmit` and the pruning logic from `prunePositionRooms` — verbatim, no
  behavior change.
- The gateway keeps `coalescePositionEmit(room, payload)` and `prunePositionRooms(now)` as thin
  one-line delegates (same signatures, same call sites, same tests) so nothing else in the file
  changed.
- `flushPositionEmit` (the actual `this.server.to(room).emit(...)` + `this.metrics` call) stayed on
  the gateway — it's gateway-specific, not part of the coalescing logic — and is wired to the new
  class via a constructor callback (`new PositionCoalescer((room, payload) =>
  this.flushPositionEmit(room, payload))`).
- Gateway's own export surface (`POSITION_COALESCE_MS`, `POSITION_ROOM_TTL_MS`,
  `PRESENCE_SCAN_INTERVAL_MS`, `PRESENCE_STALE_DEDUP_TTL_S`) stays byte-identical via a re-export
  from the new module — no import-site changes needed anywhere else in the codebase (confirmed no
  external callers of the touched methods via grep).
- `tracking.gateway.spec.ts`: one test (`prunePositionRooms` TTL test) reached into the gateway's
  private `positionEmit` map directly via a type-cast to assert on `lastEmit` timestamps. Added a
  `peek(room)` method to `PositionCoalescer` (test-only, mirrors the class's already-public `prune`)
  and updated that one test to use it instead. No other test changed.

**Proof of behavior preservation:**
