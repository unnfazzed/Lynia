# Design: Founder support sessions — act as owner in any shop

Generated by /office-hours on 2026-10-20
Branch: claude/modest-darwin-yr9yy3
Repo: unnfazzed/lynia
Status: DRAFT
Mode: Startup (intrapreneurship, internal ops tool)

## Problem Statement

The founder wants to be able to sign in to any merchant (restaurant, shop or pharmacy) and act as its
owner, to help that merchant with tasks: menu/catalogue setup, hours and open/closed, live orders,
team, Own bikers and money settings.

Today there is no way to do this:
- A merchant session is a phone-OTP JWT whose only claims are `sub` (profileId) and `role`
  (`apps/api/src/auth/token.service.ts:39`).
- The shop is worked out per request from `MerchantMember` by `resolveMerchantAccess`
  (`apps/api/src/merchant/merchant-access.ts:42`). It is called in two places:
  - `MerchantGuard` (`merchant.guard.ts:33`);
  - about nine merchant controllers that take `@CurrentUser()` profileId and re-resolve the shop
    through `merchant-lookup.util.ts`.
- The admin console (IAP/Easy Auth → shared `ADMIN_API_TOKEN` + `X-Operator` header) can:
  - approve merchants, transfer ownership, change order settings and confirm orders;
  - not edit menus, hours or open/closed;
  - not act as a merchant in any way. Nothing in the codebase impersonates anyone.

## Demand Evidence

None yet, and the founder said so: asked what happened the last time a merchant needed owner-level
help, the answer was "Not happened yet". The expected first use is onboarding new shops (setting up
the menu/catalogue for them) and covering for a kitchen that isn't answering. This is a forecast, not
an observed pain. The design keeps that in mind: build it once and properly, then let real use show
which tasks matter.

## Status Quo

No workaround in use yet. The workarounds this design exists to prevent are a merchant reading their
phone OTP to the founder (which signs the founder in as the owner's whole profile, unlogged), or a
developer editing the database by hand.

## Target User & Narrowest Wedge

- **Who:** the founder, and only the founder ("Only ever me"). There is no support-staff role and
  none is planned.
- **What, in month one:** all four task groups the founder picked: menu/catalogue setup, hours and
  open/closed, orders on the shop's behalf, and team, bikers and money.
- **Wedge:** one "Open as owner" button on the admin merchant page. It opens the real merchant app,
  in that shop, with owner powers for 60 minutes.

## Constraints

- Founder-only. The gate is the admin console's existing perimeter (IAP / Easy Auth +
  `ADMIN_CONSOLE_ALLOWED_OPERATORS`) and the admin JWT the console already uses. No new role enum.
- **Silent to the merchant** (founder decision, overriding the recommended "notify the owner"
  premise). There is no push or notification to the owner. The banner is shown only inside the
  support session.
- **New UI surfaces are undrawn.** Admin and merchant are both under the pixel-parity rule in
  CLAUDE.md (merchant aligns to `handoff/merchant-v2/`, D-77). Each new surface below needs an
  upstream drawing, or an owner-approved `docs/DESIGN-DEVIATIONS.md` entry, **before its lane
  merges**:

  | Surface | App | Path to approval |
  |---|---|---|
  | Support banner (shop, time left, Exit) | merchant | upstream drawing requested; else D-entry |
  | "Support session ended" screen | merchant | reuse the `EmptyState` pattern; D-entry |
  | "Open as owner" button | admin | D-entry (one button on the merchant detail page) |
  | Reason modal (+ override reason) | admin | reuse the existing `ConfirmModal`; D-entry |
  | Active support sessions list + Kill | admin | D-entry |
  | Session history | admin | reuse the existing merchant Audit section; no new surface |
- The phone-OTP flow, `Session` refresh rotation and `Profile` are not changed.

## Premises (agreed)

1. **Act as the shop, not as the owner's person.** A support session gets `role: owner` in exactly
   one `Merchant`. It cannot reach:
   - the owner's customer, biker or wallet endpoints;
   - the owner's other branches.
2. **Founder-only, started from the admin console.** No phone-OTP sign-in and no new roles.
3. **Bounded and audited.** Each session:
   - needs a typed reason;
   - expires after 60 minutes;
   - writes every request, reads included, to the existing `AuditLog` as "operator X, acting for
     shop Y".
4. **Visible to the operator.** The merchant app shows a persistent "LyniaGo support in <shop>"
   banner with Exit, during support sessions only.
5. **Silent to the merchant** (changed from "told, not asked" by founder decision). Must-ship
   mitigation: one sentence in the merchant terms (`apps/api/src/legal/legal.content.ts`, which
   today has no account-access clause): *"LyniaGo support may access your business account to help
   you; every access is logged."*
   - **How existing merchants are bound.** Merchant terms carry only `MerchantMember.termsAcceptedAt`
     (schema.prisma:1353) and have no version. So:
     - the PR adds a `MERCHANT_TERMS_VERSION` constant and a `termsVersion` column next to it;
     - existing owners see the new terms once, on their next merchant-app load, as the existing
       terms-accept step re-shown, and accepting stamps the version.
   - **Gate.** A support session can only start for a merchant whose owner has accepted the current
     version. Otherwise `POST admin/merchants/:id/support-session` returns
     `409 { reason: "terms_not_accepted" }` and the console says so.
   - **Exception.** The founder may override with a second typed reason (`override: true`). The
     override is audited as `support_session.start_override`. This keeps the "2am kitchen not
     answering" case possible without pretending the merchant agreed.
6. **One-way actions stay blocked inside a session**, refused with `403 { reason: "support_blocked" }`.
   There is no merchant-side ownership-transfer or business-deletion endpoint today. Ownership
   transfer exists only as `POST admin/merchants/:id/owner`, already audited in the console. The
   blocked merchant-surface endpoints are therefore the ones that act on the *person* or move outside
   the one shop:
   - `POST merchant/team/leave` (`merchant-team.controller.ts:79`);
   - `POST merchant/fleet/leave` (`fleet.controller.ts:173`);
   - `POST merchant/branches/switch` (`merchant-branches.controller.ts:32`);
   - `POST merchant/branches` (`merchant-branches.controller.ts:42`, which creates a new business
     under the owner's profile);
   - join/decline invite;
   - the new terms re-accept endpoint this feature adds (`POST merchant/terms/accept`). Only the
     real owner can stamp `termsVersion`. In a support session the merchant app shows the terms step
     as a read-only notice ("The owner hasn't accepted the updated terms yet") and never offers
     Accept, so an override session can't agree on the merchant's behalf. In a support session the
     notice is non-blocking: an inline card above the board, with the board and every other
     merchant-surface screen usable. A test asserts that an override session reaches the board while
     the owner's termsVersion is still stale. `POST merchant/terms/accept` is the only writer of
     `termsVersion`, and any existing writer of `termsAcceptedAt` is also `@SupportBlocked()`.

   **Money settings stay allowed:**
   - `PATCH merchant/cash-rule`;
   - cash confirms and disputes on orders and bookings;
   - fleet cash.

   **Default-deny for new endpoints.** Any endpoint added later that transfers ownership, deletes the
   business or changes a payout destination must carry `@SupportBlocked()`. A unit test fails if a
   route whose path matches `owner|transfer|payout|delete-business` lacks it.
7. **Invisible on the merchant side** (owner, 2026-10-20: "merchant app should not see that we are
   online"). No merchant-app surface may show that a support session exists or is live. Each leak
   path is closed explicitly:
   - **Team list.** A support session is not a `MerchantMember` and never creates one, so it never
     appears in Team (`merchant-team.controller.ts`) or as a pending invite.
   - **Devices and sessions.** No `Session` row is created and the OTP path is never touched. So there
     is no "signed in on another device" signal and no new-device identity alert
     (`auth.service.ts:803`).
   - **Kitchen presence.** The support socket joins only that shop's order-update rooms, **never** the
     kitchen queue/presence room that `TrackingGateway.isMerchantOnline` reads
     (`tracking.gateway.ts:579`, `queue-socket.ts`). So the shop never looks "online" or "tablet
     connected" because of you. That check has no live callers today (owner decision D1). The test
     still asserts that a support socket is absent from the presence room, so a future caller can't
     count you.
   - **Cross-device sync.** Branch switching is blocked (premise 6), so the MJ-RM15 "another device
     switched this branch" follow (`apps/merchant/app/(app)/layout.tsx:44`) never fires on the
     owner's tablet.
   - **Notifications.** Starting, using or ending a session sends no push, SMS, email or in-app
     message to any merchant device.
   - **Attribution.** Actions you take show in the merchant app as the shop's own actions. The order
     moves, the dish changes, with no "by LyniaGo support" label. Where a merchant-visible record
     names an actor (for example an order timeline), it shows the shop name, never the operator.
   - **Audit.** `AuditLog` is read only by the admin console (`GET admin/audit`). No merchant endpoint
     returns support rows.
   - **What stays visible, unavoidably:** the *effects* of what you do. An accepted order, an edited
     price and a closed shop all look the same as if the owner had done them.

   Tests: a support session leaves Team, the sessions list and the presence room unchanged. No
   notification is enqueued for any merchant member during a session.

## Approaches Considered

- **A) Minimal support token.** A 60-min JWT plus one-time code, pinned to the shop. There is no
  session table, so it can't be revoked and has no per-action trail. Rejected: a leaked link would
  be an unrevocable key.
- **B) Complete support session.** Chosen (below).
- **C) Admin-native editors.** Rebuild menu, hours, orders and team inside `apps/admin`. Rejected: it
  duplicates the merchant app and drifts from the design handoffs.

## Revision 2026-10-20: admin side only (owner, overrides the merchant-app parts below)

Owner, 2026-10-20: *"no new features merchant side, only admin side is changed"*. That instruction
changes the design as follows:

- **`apps/merchant` is not changed at all.** The entry page, cookie, banner, "session ended" screen
  and terms re-accept step described below are **not built**.
- **You work from the admin console.** The console gets an **Open as owner** workspace for one shop:
  - Orders (live board and actions);
  - Menu (categories and items);
  - Shop (open/closed, busy mode, hours);
  - Team;
  - Money (cash rule, weekly statement).
  It calls the API's **existing** `merchant/*` endpoints, so every owner rule stays in one place.
- **No support token.** The admin console's server calls `merchant/*` with its admin token plus
  `X-Support-Session: <id>`. The API checks the session, then acts as the shop's owner pinned to that
  one shop. The rules from the original design still hold:
  - refused outside `merchant/*`;
  - blocked routes (premise 6);
  - every request audited, with the audit write fail-closed;
  - one active session per shop.
- **No socket.** The workspace refreshes on a timer, so the kitchen-presence leak (premise 7) cannot
  happen.
- **Terms gate dropped.** Re-accepting terms would be a merchant-side change. Silent access rests on
  the audit log, and adding the terms clause stays an open question for a later export.
- **The new admin screens** are designed by Claude (owner instruction) in the existing console style
  and recorded as one `docs/DESIGN-DEVIATIONS.md` entry.

## Recommended Approach: B — complete support session (original; see the revision above)

### Data
New Prisma model `SupportSession`:
- `id`
- `merchantId` (FK)
- `operator` (the `X-Operator` identity)
- `reason` (required, ≤ 280 chars)
- `codeHash` (one-time exchange code, single use, expires 2 min after mint)
- `createdAt`
- `expiresAt` (createdAt + 60 min)
- `endedAt?`
- `endedReason?` (`exit` | `expired` | `killed`)

Plus one migration.

### API (`apps/api`)
1. **Start a session.** `POST admin/merchants/:id/support-session { reason }` (AdminGuard). It
   creates the row, returns a one-time code, and writes `AuditLog` `support_session.start`.
2. **Exchange the code.** `POST auth/support/exchange { code }` (public).
   - The code is 32 random bytes, base64url, and only its SHA-256 is stored.
   - The endpoint is rate-limited to 10 requests/min per IP.
   - It verifies the hash, single use and the 2-minute window, then mints a **support access token**:
     - `sub` = a synthetic id `support:<sessionId>`, not the owner's profileId;
     - `kind: "support"`;
     - `sid`, `mid`;
     - `exp` = session `expiresAt`;
     - no refresh token.
   - **`kind: "support"` is a token-only principal kind.** It is *not* added to the Prisma `Role`
     enum or `Profile.role`, and the token carries no `role` claim. Existing role guards
     (`AdminGuard`, rider and customer checks) compare `role` and so fail closed on it.
   - `@CurrentUser()` keeps returning a string, but its type becomes
     `ProfileId | SupportPrincipal`, so a service that needs a real profile must handle the support
     case explicitly (see item 4).
3. **`JwtAuthGuard`.** For `kind: support`:
   - load the session on every request and reject it if it has ended or expired (this is how
     revocation works);
   - allow only routes on controllers carrying a `@MerchantSurface()` class decorator. One mechanism,
     no allowlist;
   - refuse everything else (customer, rider, wallet, admin, auth).
   - A test walks Nest's `DiscoveryService` route table and asserts that a support token gets
     401/403 on every route not under `@MerchantSurface()`.
4. **One seam for "which shop".** `resolveMerchantAccess` (or a request-scoped context it reads)
   returns `{ merchantId: mid, role: "owner", support: { sessionId, operator } }` for a support
   principal. This covers both `MerchantGuard` and every `@CurrentUser()`-then-lookup controller.
   - **Plan-eng-review must enumerate the merchant services that use the profileId for anything else**
     (writing `createdBy`, `leave team`, `join`, branch switching) and decide each one.
   - `leave`, `join`, `decline` and branch switching are refused in a session (premise 6).
   - **Default rule until each service is classified:** a write that records a profileId (for
     example `createdBy` or `addedByProfileId`) records the **shop owner's profileId**, and the audit
     row carries the support sessionId. A service that would otherwise receive `support:<id>` as a
     profile FK throws in tests, so no synthetic id ever reaches the database.
5. **Audit, fail-closed, every request.** An interceptor runs on every request under a support
   principal, reads included. Reads are logged too because owner powers in a pharmacy expose
   prescription images and customer phone numbers and addresses, and with silent access the log is
   the only record.
   - **Before the handler,** it inserts an `AuditLog` row:
     - `actor = operator`;
     - `action = support.<METHOD> <route template>`, e.g. `support.PATCH /merchant/dishes/:id`;
     - `target = merchantId`, `targetType = merchant`;
     - `note = sessionId`.
     If that insert fails, the request is refused with `503` and the handler never runs.
   - **After the handler,** it updates the row with the status code. Before/after is recorded where
     the service already exposes it.
   - **What gets logged:** rejected attempts, including `403 support_blocked`, and 4xx/5xx
     responses. Start, exit, expiry, kill and override are logged too.
   - **Volume** is fine because there is one operator.
6. **Blocked actions, enforced after the audit insert.** Nest runs guards before interceptors, so a
   refusal made in a guard would never reach the audit row.
   - **`@SupportBlocked()`** is therefore metadata only, and the **audit interceptor** enforces it:
     1. insert the row;
     2. if the route carries `@SupportBlocked()`, update the row to 403 and throw
        `403 { reason: "support_blocked" }`.
   - **`JwtAuthGuard` refusals** of a support token on a non-`@MerchantSurface()` route happen in the
     guard, so the guard writes its own `AuditLog` row (`support.refused <route template>`) before it
     throws. If that insert fails, the request is still refused.
   - Both paths have tests that assert the row exists, with one test per blocked endpoint.
7. **Live orders.** `tracking.gateway.ts handleConnection` (`:159`) accepts a support token and joins
   only that merchant's rooms. Disconnect has two mechanisms, both covered by tests:
   - **Expiry:** on connect, a per-socket `setTimeout` to `expiresAt` disconnects the socket.
   - **Kill (cross-instance, ≤ 5 s):** every 2 s each API instance re-checks its connected support
     sockets against `SupportSession` with one query: `endedAt IS NOT NULL` for the ids it holds.
     It disconnects any that have ended. This needs no pub/sub and works on any number of
     instances.
   - Socket connect and disconnect under a support token each write an `AuditLog` row with the
     sessionId.
8. **One session per shop.** Starting a session while one is active for that merchant returns
   `409 session_active`. Concurrent founder and owner actions rely on the existing order-state
   transition checks, which already refuse a second accept.
9. **Admin endpoints.**
   - `GET admin/support-sessions?active=1` lists sessions.
   - `POST admin/support-sessions/:id/kill` ends one.

### Admin console (`apps/admin`)
- On the merchant detail page, an **Open as owner** button opens a reason modal, then
  `window.open(<merchant-app>/support/enter?code=…)`.
- An **Active support sessions** list with Kill.
- Session history from `GET admin/audit` filtered to `support.*`.

### Merchant app (`apps/merchant`)
- **Entry, made same-site on purpose.** `/support/enter?code=` is a static client page. A cross-site
  `window.open` lands on it with no cookies needed.
  1. On load it calls `history.replaceState` to strip the code from the URL. The page sends
     `Referrer-Policy: no-referrer`.
  2. It POSTs the code, same-origin, to a Next route handler (`/api/support/exchange`). The handler
     calls the API and sets the cookie in its response.
  3. It then navigates **client-side** (`router.replace("/")`). Every load from then on is started by
     the merchant origin itself, so a `SameSite=Strict` cookie is sent.
  - An end-to-end Playwright test opens the merchant app from an admin origin and asserts the board
    loads in that shop.
- **Cookie.** The support token goes in a **separate** `httpOnly`, `SameSite=Strict`, session-scoped
  cookie (`lynia_merchant_support`). It never overwrites a real `lynia_merchant_session` on that
  browser.
- **Precedence.** When `lynia_merchant_support` is present, the API client sends **only** the support
  token and ignores `lynia_merchant_session` entirely, including refresh.
  - When the session ends (Exit, 401, expiry), the support cookie is cleared and the app shows the
    "Support session ended" screen. It **never** falls back to the real session or the OTP sign-in.
  - A test covers both cookies being present.
- The persistent support banner shows the shop name, time left and Exit. Exit calls
  `POST merchant/support-session/exit`, which sits on a `@MerchantSurface()` controller so a support
  token can reach it, and ends the session server-side.
- A real merchant session on the same browser is shadowed (not altered) during a support session and
  resumes after it ends.

## Open Questions

2. **Session length.** Is 60 min right for menu onboarding, which can take longer? Add an "Extend

## Success Criteria

- The founder clicks Open as owner on any merchant. Within 10 s the merchant app is open in that
  shop's board with owner powers, and live orders tick over the socket.
- A support token is refused (401/403) on every non-merchant route. Tests cover:
  - a customer route;
  - a rider route;
  - a wallet route;
  - an admin route;
  - `/auth/refresh`.
- Killing a session in the admin console makes the next API call 401 and drops the socket within
  5 s.
- Every request in a session appears in `GET admin/audit` with operator, shop, route and sessionId.
  This is proven by a test that edits a dish and asserts the row.
- Each premise-6 endpoint returns `403 support_blocked` inside a session (one test each), and the
  attempt is in the audit log.
- Opening a prescription image in a support session writes an audit row.
- An audit-insert failure returns 503 and the mutation does not happen (test).
- Starting a session for a merchant who hasn't accepted the current terms returns
  `409 terms_not_accepted` unless an override reason is given.
- Existing merchant OTP sessions on the same browser are untouched after a support session.
