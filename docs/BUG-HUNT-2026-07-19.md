## Sibling-sweep

**BH-21** — pattern signature: a session-only `useState<Set<...>>` recording "have I already acted on
this" that gates a live list/board filter, with no persistence and no expiry check.

```
grep -rn "useState<Set" apps/mobile/app apps/mobile/src --include=*.tsx --include=*.ts | grep -v __tests__
grep -rn "this session\|this app session" apps/mobile/app apps/mobile/src --include=*.tsx --include=*.ts | grep -v __tests__
```

6 hits. Disposition of each:

- `rider/index.tsx` `bidIds` / `sentOffers` — the confirmed bug, fixed above.
- `order/[id].tsx:86` `declinedCounterIds` — a customer-side "dismiss this counter-offer card"
  flag (`isPendingCounter`'s `!declined` term), same session-only shape. Traced the consequence: a
  process death resets it, so a previously-dismissed counter-offer card reappears with Accept/Decline
  controls on relaunch — annoying (repeats information the customer already dismissed) but **not** a
  dead-end, **not** data loss, and **not** financially incorrect (the counter is still genuinely live
  server-side either way; the customer can just decline it again, or accept it if they've changed
  their mind, which is a legitimate action). Judged materially lower severity than BH-21 (which hid an
  ACTIVE FINANCIAL COMMITMENT — the rider's own sent bid — and could let a rider accidentally re-bid
  into a board slot they'd already filled). Left unfixed this run rather than adding a third
  SecureStore-persistence key for a cosmetic repeat; logged below as `BH-21-SIB-1` (OPEN, LOW) per the
  sibling-sweep evidence rule.
- `rider/job.tsx:63` `checkedItems` — already-guarded: has its own persisted mirror
  (`savePickupChecklistDraft`/`loadPickupChecklistDraft`, keyed to the order, restored on mount).
- `rider/job.tsx:135` and `rider/index.tsx:222` `ackedHandbacks` — already-guarded: both hydrate from
  `loadAcknowledgedHandbacks` (`auth/session.ts`), a genuine SecureStore-backed store, not a bare
  `useState`.
- `use-rider-board.ts` `expiredOrderIds` / `takenOrderIds` — reviewed and confirmed NOT a sibling: the
  underlying `["openOrders"]` query itself is explicitly excluded from the app's disk-persisted query
  cache (`query/persist.ts`'s `PERSISTED_KEY_ROOTS` allowlist deliberately omits it — "LIVE marketplace
  state... stays memory-only and is always fetched fresh"), so a cold start always re-fetches a fresh
  board with no stale expired/taken orders in it to mis-flag in the first place. These two Sets
  correctly reset in lockstep with the data they annotate.

**BH-22** — pattern signature: a user-initiated `prisma.<model>.create(` reachable from a mobile
`useMutation` retry, with no idempotency key and no natural uniqueness constraint standing in for one.

```
grep -rn "prisma\.\w*\.create(" apps/api/src --include=*.ts | grep -v spec
grep -rn "\.create(" apps/api/src --include=*.ts | grep -v spec | grep -v "prisma\."
grep -rln "idempotencyKey" apps/api/src apps/mobile/src packages/shared/src
```

7 top-level `prisma.*.create` call sites + ~35 `tx.*.create` call sites inside transactions. Every
other user-retriable creation path was traced and confirmed already-guarded:

- `Order.create` / `TopUp.create` — already have `idempotencyKey` (BUG-HUNT / BH-09 precedent this fix
  mirrors).
- `Offer.create` (`offers.service.ts:111`, rider's bid) — guarded by the DB-level `@@unique([orderId,
  riderId])` "one round per rider" constraint itself; a retry hits `P2002` and the service already
  maps it to a clean 409 the mobile client already reconciles gracefully (`rider/index.tsx`'s
  `onError` handler, pre-existing). Structurally can't double-create.
- `Report.upsert` (`reports.service.ts:51`) / `Block.upsert` (`:76`) — genuine upserts on a compound
  unique key, not creates. Structurally can't double-create.
- `Rating.create` (`order-lifecycle.service.ts:572,692`) — guarded by the migration-0015 composite
  unique `(order_id, by_profile_id)` re-verified intact in this run's own Phase-0.5 pass above.
- `Rider.create` (signup, `rider.service.ts:180`) — guarded by the `profileId` primary key + an
  explicit `P2002`→409 mapping (DS13-06 precedent), same shape as the offer guard.
- `SosEvent.create` (`sos.service.ts:58`) — reviewed and confirmed **intentionally** not deduped: the
  SOS control's own code comment states duplicate alerts are the deliberately safe failure mode
  ("the alert is not one-shot... a SECOND SOS later in the same trip re-arms... re-alerts ops",
  `safety.tsx:443-444`), and the `useEffect` firing it is gated on `m.isIdle` so a single sheet-open
  fires exactly once regardless of network timing — only a deliberate close+reopen re-fires it. Not a
  sibling of the double-refund-risk class BH-22 fixes.
- `AuditLog.create` / `OrderEvent.create` / `CommissionLedger.create` (various) — internal
  system-of-record writes inside already-guarded transactions (CAS/row-lock), never a bare
  user-retriable top-level create.

`Issue.create` was the sole genuine gap — fixed above, no sibling left unaddressed.
