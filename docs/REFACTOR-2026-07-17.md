## Phase 2 — RF-02: extract `NotificationsFeedService`

`apps/api/src/notifications/notifications.service.ts` bundled two unrelated concerns: the push
write-path (`notify*` methods, device-token registry, the private `send()` fan-out) and the
in-app notifications feed — a pure **read model** (`feedForUser`) that never touches the push
adapter, built entirely from `PrismaService` queries over orders/offers/audit logs/issues/SOS
events.

**What moved**, verbatim, into new `apps/api/src/notifications/notifications-feed.service.ts`:
- `NotificationRow` interface
- `FEED_NOTICES`, `FEED_NOTICES_RIDER`, `ACCOUNT_FEED_COPY`/`ACCOUNT_FEED_ACTIONS`,
  `ISSUE_RESOLUTION_FEED_COPY`, `FEED_UNREAD_WINDOW_MS`, `FEED_ORDER_LOOKBACK`, `FEED_ROW_CAP`
- `feedForUser(userId, now)` — full body, unchanged

**Wiring:**
- `notifications.module.ts` — added `NotificationsFeedService` to `providers`/`exports`
  (still `@Global()`, same as `NotificationsService`).
- `notifications.controller.ts` — now injects both services; `GET /notifications/feed` calls
  `this.feedService.feedForUser(profileId)` instead of `this.notifications.feedForUser(profileId)`.
  Route path, method, guard, and response shape are unchanged.
- No other call sites needed touching: `feedForUser`/`NotificationRow` had zero external
  importers (the controller was the only caller; mobile's `notifications.ts` already carries its
  own local `NotificationRow` shape). Mentions of `feedForUser` in `rider.service.ts`,
  `admin-riders.service.ts`, `admin-audit.service.ts` are comments only.

**Tests:** the 18-case "derived in-app feed (A·3)" describe block moved verbatim from
`notifications.service.spec.ts` into a new `notifications-feed.service.spec.ts`, with its own
`makeDeps()` needing only a `PrismaService` mock (no push adapter — the feed never sent a push).
The original spec's `makeDeps()` was trimmed of the now-unused `offer`/`auditLog`/`issue`/
`sosEvent` prisma mocks (kept `order.findMany`, still used by `notifyRidersAvailable`'s
KB-NOTIFY-ORDERID open-order lookup). Total test count is unchanged: 1010 API tests before and
after (46 notification-area tests: 18 in the new file + 28 in the trimmed original, same as the
46 that existed pre-split).

**Over the ~400-changed-line guideline, deliberately.** Diff: 6 files, 832 insertions / 800
deletions. The 2026-07-15 ledger estimate (~470 lines) was stale — the feed slice had grown 25%
in the two days since (four UX-routine features landed on it). This is still the right call to
ship as one PR rather than split further: it is a byte-identical, single-concern move (nothing
was rewritten, only relocated — the diff's per-line risk is far below a normal-sized PR of
equivalent line count), and splitting the move itself (e.g. constants in one PR, `feedForUser`'s
body in a follow-up) would leave the concern half-extracted across two PRs — a worse trade than
one larger mechanical diff with 100% pre-existing test coverage carried over intact.
