## Phase 1 — the work: RF-14, reconciler-sweep commit dedup

`apps/api/src/merchant/food-order.service.ts` runs four DB-only reconciler sweeps every 20s
(`RESTAURANTS_TIMING.sweepIntervalMs`). Three of them — `sweepExpiredAcceptWindows` (N-03),
`sweepExpiredPhase` (the generic helper `sweepExpiredItemApprovals`, N-18, already called into),
and `sweepEndOfDayClose` (N-23) — each inlined the identical "commit" tail once a stale order was
found: a CAS `updateMany` guarded by `status: "requested"` plus the caller's own extra guard
(`acceptDeadlineAt` equality, `merchantPhase: phase`, or nothing extra for the fixed
`awaiting_payment` phase), and on a successful claim, write the `orderEvent`, push
`notifyCancelledCustomer`, and push `notifyQueue` — differing only in the extra `where` guard and
the `rejectionReason`. Extracted that tail into one private helper:

```ts
private async commitStaleCancellation(
  orderId: string,
  merchantId: string | null | undefined,
  whereExtra: Prisma.OrderWhereInput,
  reason: MerchantRejectionReasonCode,
): Promise<boolean> {
  const claimed = await this.prisma.order.updateMany({
    where: { id: orderId, status: "requested", ...whereExtra },
    data: { status: "cancelled", cancelledAt: new Date(), rejectionReason: reason, merchantPhase: null },
  });
  if (claimed.count === 0) return false;
  await this.prisma.orderEvent.create({ data: { orderId, status: "cancelled" } });
  await this.notifyCancelledCustomer(orderId, reason);
  this.notifyQueue(merchantId, orderId);
  return true;
}
```

Each of the three callers now does its own query, its own row-level `try`/`catch` (error-message
prefix unchanged per sweep, e.g. `sweepExpiredAcceptWindows failed for order ${o.id}`), and its own
counter increment, calling `commitStaleCancellation` in place of the inlined block. The `where`
clause passed as `whereExtra` reproduces each caller's original CAS guard exactly (object key order
doesn't affect Prisma's query semantics), and the `data` object, the post-claim write order
(`orderEvent` → `notifyCancelledCustomer` → `notifyQueue`), and the `claimed.count > 0` success
check are all byte-identical to what each caller had inline before.

`sweepExpiredAcceptWindows` keeps its distinct pre-check (the merchant-online pause branch) ahead
of the shared commit call — untouched, since that logic decides whether to even attempt a
cancellation, not how to commit one. `sweepEndOfDayClose` keeps its distinct pre-check (the
per-order `isPastClosingTime` filter against fetched merchant hours) for the same reason.

`sweepPaymentReminders` (N-22) was deliberately **not** touched: it claims via
`paymentReminderSentAt: null` and sends a reminder push, not a cancellation — it doesn't fit the
"CAS-cancel and notify" shape the other three share, and forcing it into the same helper would
relocate its distinct claim semantics rather than reduce duplication.
