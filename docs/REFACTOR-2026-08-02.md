## Phase 1 — the work: RF-05b's design-note follow-up

Read `apps/api/src/tracking/tracking.gateway.ts` in full (870 lines) to verify, rather than
re-assert, the 2026-07-26 run's entanglement finding. Traced every read/write of the four remaining
structures (`staleNotified`, `customerStaleNotified`, `customerPresence`, `customerSocketOrders`)
and every cross-boundary call their six owning methods make (`handleDisconnect`, `subscribeOrder` +
`markCustomerPresent`, `syncCustomerPresenceToRider`, `scanPresence`, `scanCustomerPresence`,
`customerLiveInRoom`, `riderLiveInRoom`):

- 2 direct Socket.IO server queries (`server.in(room).fetchSockets()` in `customerLiveInRoom`/
  `riderLiveInRoom`) — a live transport dependency, not a data structure.
- 2 gateway emit methods (`emitPresenceStale`/`emitPresenceRecovered`), called from 3 different
  sites at points chosen by the surrounding conditional logic, not one flush boundary.
- 6 distinct `TrackingService` calls (`findStaleRiderPresence`, `releasePresenceEscalation`,
  `claimPresenceEscalation`, `touchRiderHeartbeat`, `filterActiveOrders`, `assignedRiderId`),
  interleaved inside the same scan-loop bodies that read/write the maps.

That's ~10 cross-boundary calls interleaved with map mutations inside conditional branches across
two subsystems (the Socket.IO transport and `TrackingService`'s escalation-claim state machine) —
materially different from RF-05a's `positionCoalescer`, which crossed back into gateway territory
at exactly one point (the flush callback). **Decision: the gateway keeps this half.** A
narrow-interface extraction here (~10-method port) would relocate complexity rather than reduce it,
on the single most bug-history-dense file in the repo (most `BH-`/`DS-` `KNOWN_BUGS.md` entries
trace back to this gateway) — that fails the routine's own bar for a hotspot refactor. **RF-05b is
resolved WONT-DO (extraction)**, reclassified as correctly gateway-resident presence-watchdog logic,
not misplaced logic waiting to move. Full reasoning: `docs/RF-05-WS-GATEWAY-STATE.md`.

Also closed the design doc's other two open items while re-reading the file:

- **RF-05c** (per-process-guarantee comments on `staleNotified`/`customerStaleNotified`): added —
  2 comment-only edits, no logic change.
- **`customerPresence`-authority verification** (the design doc's original step 2, "needs
  verification"): traced every read site. `scanCustomerPresence` only uses the local map to narrow
  which orders get the expensive cluster-wide `customerLiveInRoom` check — every actual escalation
  is gated by that fetchSockets-backed check immediately before `emitPresenceStale` fires, so a
  customer connected to a different instance is caught and corrected, never falsely escalated.
  `syncCustomerPresenceToRider` only reads local state to sync a socket that, by construction, just
  subscribed on *this* instance — no cross-instance read there either. **Confirmed cache, not
  authority; no code change needed.**

RF-05 as a whole is now **DONE** — RF-05a/b/c all have a terminal disposition, closing the ledger
