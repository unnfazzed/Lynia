## Phase 1 — priority order (a): first actionable OPEN row

RF-21's design pass (`docs/RF-21-SEND-SCREEN.md`) named the next increment explicitly: extract the
`accountOnHold` early-return (lines 590-608 of `apps/mobile/app/send.tsx`) into a new
`SendAccountOnHoldView` — a full alternate screen, ~6 bounded props (`activeOrder`,
`activeOrderQ.isError`/`isFetching`/`refetch`, `meQ.isFetching`/`refetch`), no local state, no
draft-persistence/idempotency/submit coupling (a held account can't reach `submit()` — the wall
replaces the whole screen). Same risk profile as RF-18's first extraction.

**Executed exactly that.** Moved the branch verbatim to a new
`apps/mobile/src/ui/send/SendAccountOnHoldView.tsx`, following the `apps/mobile/src/ui/food/*`
extraction convention (RF-18). The branch's own local helper, `ActiveOrderBanner` — previously
defined inline in `send.tsx` and reused by both the on-hold wall and the main compose form's own
active-order banner — moved into the new file too (it's a small presentational component with no
reason to live in the route file once one of its two call sites moves out); `send.tsx` now imports
it back for its own remaining usage. No prop or behavior changed at either call site.

**Characterization tests added first**, per the routine's "uncovered code gets tests first, same
PR" rule: the existing `app/__tests__/send.test.tsx` covered only the LC-C06 draft-flush path, not
the `accountOnHold` wall at all. Added 3 cases pinning the wall's exact pre-extraction behavior —
on-hold copy + support-call row + refresh-calls-`meQ.refetch()`; the active-order restore banner
rendering instead of (in front of) the wall's default state when a live order exists while held;
and the active-order-check-failure banner + retry-calls-`activeOrderQ.refetch()` path — before
moving the JSX, so a behavior regression in the move would have failed these tests rather than
going unnoticed.
