## Phase 1 — RF-15 re-investigation: mostly a false positive

RF-15 claimed six near-identical `Row({label, value})` components across
`apps/mobile/app/{food/order/[orderId],food/cart,history/index,notifications/index,settings/index,
rider/documents}.tsx` worth consolidating into `src/ui`. Reading all six bodies:

- `food/cart.tsx` and `food/order/[orderId].tsx` are genuinely the same shape — a two-column
  `label`/`value` row. But they aren't byte-identical: `cart.tsx`'s non-bold value renders at
  `fontSize: 13.5`, while `[orderId].tsx`'s (single, non-bold-only) value renders at a fixed
  `14.5` — a deliberate-looking size difference (order-detail totals get more visual weight),
  not accidental drift.
- `history/index.tsx`'s `Row({o, onPress, onReorder})` renders an order-history card (route,
  date, fare, status pill) — a different component entirely.
- `notifications/index.tsx`'s `Row({n, onPress})` renders a notification tile (icon, title,
  message, unread state) — different again.
- `settings/index.tsx`'s and `rider/documents.tsx`'s `Row(props: {icon, label, value, ...})` both
  take an icon and render list items, but one is pressable with a danger variant (settings) and
  the other shows a verification status pill (documents) — related in spirit, not in code.

Net: 4 of the 6 are unrelated components that happen to share the name `Row`; the 2 genuine
matches differ in a value that looks like a deliberate design choice, and unifying them would need
a style-override prop just to preserve both exact renders — for two ~7-line functions, that's more
indirection than duplication removed. **Resolved WONT-DO**, findings recorded in the ledger so a
future churn spike on these files doesn't re-raise the same false lead.

**Then the dedup.** The file had 4-5 near-identical busy+error `try`/`catch`/`finally` wrappers:
`PaymentBucketActions`'s generic `run(thunk)` (shared by 3 buttons) and its `submitConfirm` (closes
the sheet on success), `RefundAction`'s promise-chain confirm handler (closes its sheet on
success, and uniquely has no "— try again." suffix on its fallback), and `OrderCard`'s
`handleMarkReadyClick`/`handleRevealClick` (the latter stores the resolved pickup code on
success). Collapsed into one local hook:

```ts
function useAsyncAction(fallbackMessage = "Something went wrong — try again.") {
  const [busy, setBusy] = useState(false);
  const [error, setError] = useState<string | null>(null);
  async function run<R>(action: () => Promise<R>): Promise<{ ok: true; value: R } | { ok: false }> {
    setBusy(true);
    setError(null);
    try {
      const value = await action();
      return { ok: true, value };
    } catch (err) {
      setError(err instanceof Error ? err.message : fallbackMessage);
      return { ok: false };
    } finally {
      setBusy(false);
    }
  }
  return { busy, error, setError, run };
}
```

`run` takes its thunk at call time (not bind time), which is what lets `PaymentBucketActions` back
3 distinct buttons off one shared busy/error pair — exactly the state sharing the
pre-extraction code had. Each of the 4 call sites now does its own thin wiring on top: `submitConfirm`
and `RefundAction`'s handler check `result.ok` before closing their sheet; `handleRevealClick`
checks `result.ok` before storing `result.value` as the pickup code; `RefundAction` passes its
distinct fallback string as the hook's argument. Nothing about button disabled-states, busy-label
text, error-message text/placement, or click-to-callback argument wiring changed — the 23
characterization tests pass unmodified against the post-extraction code.
