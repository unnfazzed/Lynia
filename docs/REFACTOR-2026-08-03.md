## Phase 1 — RF-18: second extraction from the food-order tracking screen

The prior run's note: "remaining ~7 branches ... several read heavy component-local state ... so a
clean extraction is more involved than a verbatim move." Re-reading the 791-line screen confirmed
that's true for only 3 of the remaining branches — `awaiting_payment`'s 3 sub-cases, the live
tracker, and delivered/completed all close over `busy`/`error`/`forcePayScreen`/`cancelConfirm`/
`deliveryCode`/`pendingRating` state or their setters directly inline. The other **four** remaining
branches are, like the first run's `cancelled`/`undelivered`, pure functions of `order` fields plus
values already threaded in as props (`now`, `error`, `busy`, `reachable`, `restaurantName`) — no
hooks, no state reads beyond what's passed in:

- **`awaiting_accept`** (23 lines) — N-03's 3:00 kitchen-accept countdown ring. Reads only
  `order.acceptDeadlineAt`, `now`, `restaurantName`, `reachable`, `error`, and the pre-built
  `CancelFooter` element (itself already a prop-like value computed once above every branch).
- **`awaiting_item_approval`** (35 lines) — D-23 item-level accept, N-18's 60s approval window.
  Reads `order.itemApprovalDeadlineAt`/`order.items`, `now`, `restaurantName`, `reachable`, `error`,
  `busy`; the two buttons call back into the screen's `approveItems(approve)` closure via an
  `onApprove` callback prop, same shape as the first extraction's `onRetry`/`onBrowse`.
- **`preparing`** (22 lines) — D-03's cooking countdown ring sitting above the shared seven-step
  `Stepper`. Reads `order.prepMinutes`/`order.prepStartedAt`/`order.status`, `now`,
  `restaurantName`, `reachable`. No error/busy touched at all.
- **`ready_for_pickup`** (24 lines) — N-08 dispatch-searching / N-07 hold-after-cap. Reads
  `order.noRiderHoldAt`/`order.status`, `restaurantName`, `reachable`, `error`.

Moved verbatim (JSX, copy, prop-driven logic byte-identical) into four new presentational
components under `apps/mobile/src/ui/food/`: `FoodOrderAwaitingAcceptView.tsx`,
`FoodOrderItemApprovalView.tsx`, `FoodOrderPreparingView.tsx`, `FoodOrderReadyForPickupView.tsx`.
Each takes a narrow `Pick<MerchantOrderResponse, …>` of only the fields it reads (matching the
first extraction's `FoodOrderCancelledView`/`FoodOrderUndeliveredView` convention) plus the already-
computed scalars/callbacks as props — no new state, no new effects. They reuse the existing
`OrderHeader` (from `FoodOrderHelpers.tsx`), `CountdownRing`/`formatCountdown`, and `PriceMath`
exactly as the inline JSX did; `PriceMath` and `CountdownRing`/`formatCountdown`/`RESTAURANTS_TIMING`
are consequently no longer imported by the main screen file (only the 3 still-inline branches would
have needed them, and none do).

The four in-screen branches now read as one-line delegations, e.g.:

```tsx
if (order.merchantPhase === "preparing") {
  return <FoodOrderPreparingView order={order} restaurantName={restaurantName} reachable={reachable} now={now} />;
}
```
