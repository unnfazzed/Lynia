## Phase 1 — RF-18: third (final) extraction from the food-order tracking screen

The twelfth run's note: the remaining 3 branches (`awaiting_payment`'s sub-cases, the live
tracker, delivered/completed) "read heavy component-local state ... need a real design pass, not a
verbatim move." Re-reading the 714-line screen confirmed the state-reading part — unlike the first
two extractions' branches, these three genuinely close over `busy`/`error`/`forcePayScreen`/
`referenceInput`/`cancelConfirm`/`deliveryCode`/`confirmCashBusy`/`rateBusy`/`pendingRating` (state
or setters) or refs (`ratingFromStorage`) directly — but the "design pass" itself turned out to be
the same interface the second extraction's `onApprove` callback prop already established, just with
more props per view, not a new pattern:

- **`awaiting_payment`** (98 lines, 4 sub-cases: paid-waiting on the restaurant's confirm, the
  still-unpaid N-22 free-cancel reminder, "kitchen calls first," and the manual pay rail + "I paid
  another way" reference submission) — reads `busy`/`error`/`now`/`forcePayScreen`/
  `referenceInput` plus the pre-built `CancelFooter` element (same prop the first two extractions
  already thread through), and calls back via `onForcePay`/`onReferenceChange`/`onSubmitReference`/
  `onCancelFree`.
- **Live tracker** (117 lines — rider-secured banner, the generic order-snapshot tracking card,
  the CASH doorstep handshake + delivery code once at the door, the post-dispatch confirm-first
  cancel) — reads `now`/`error`/`busy`/`trackQ.data`/`deliveryCode`/`confirmCashBusy`/
  `cancelConfirm`, calls back via `onConfirmCash`/`onRevealCode`/`onCancelConfirmChange`/
  `onCancelActive`. The three status-keyed lookups used only inside this branch
  (`CUSTOMER_CANCELLABLE`, `POST_PICKUP_CANCEL` sets, `TRACK_STATUS_LABEL` map) moved into the new
  view file with it; `ACTIVE` (the set the *screen* uses to decide whether to render this branch at
  all) stayed in the screen.
- **`delivered`/`completed`** (50 lines — rating card + terminal summary) — reads `rateBusy`/
  `error`/`trackQ.data?.events` (to find the `delivered` event's timestamp), calls back via
  `onRate`/`onArmRating`/`onUndoRating`/`onOrderElsewhere`. The `onArmRating`/`onUndoRating`
  callback bodies (which touch `ratingFromStorage.current`, `pendingRating`, and
  `savePendingRating`/`clearPendingRating`) stayed in the screen, passed down as closures — same
  shape as the screen's other callback props.

Moved to three new presentational components under `apps/mobile/src/ui/food/`:
`FoodOrderAwaitingPaymentView.tsx`, `FoodOrderLiveTrackerView.tsx`, `FoodOrderDeliveredView.tsx`.
Each JSX body is byte-identical to the code it replaced; only the data source changed (state →
props, closures → callback props). All three reuse the existing `OrderHeader`/`Row`
(`FoodOrderHelpers.tsx`), `CashHandshakeCard`, `DeliveryCodeCard`, `ManualPayRail`, `LiveTrackingCard`,
`RatingCard`, `GetHelpControl`/`SosControl` exactly as the inline JSX did — none of those shared
components changed.

The three in-screen branches now read as thin delegations, e.g.:

```tsx
if (order.merchantPhase === "awaiting_payment") {
  return (
    <FoodOrderAwaitingPaymentView
      order={order}
      restaurantName={restaurantName}
      reachable={reachable}
      now={now}
      error={error}
      busy={busy}
      forcePayScreen={forcePayScreen}
      onForcePay={() => setForcePayScreen(true)}
      referenceInput={referenceInput}
      onReferenceChange={setReferenceInput}
      onSubmitReference={() => void submitReference()}
      onCancelFree={() => void cancelUnpaid()}
      cancelFooter={CancelFooter}
    />
  );
}
```
